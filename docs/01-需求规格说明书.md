## 1 引言

### 1.1 编写目的

本文档面向“吃了么”外卖平台的开发、测试与验收环节，明确系统的业务边界、角色职责、功能需求与非功能需求，为后续的系统设计、编码实现与测试用例编写提供唯一依据。

### 1.2 项目背景

移动互联网的快速发展带动外卖行业持续扩张，外卖已经成为居民日常生活重要的消费方式。当前主流外卖平台功能庞大复杂，对中小餐饮商户入驻运营成本较高，平台佣金、配送调度、权限管理等方面仍存在不少待优化点。

本课题来源于社会生产实践，针对**社区中小型餐饮经营场景**，设计开发“吃了么”外卖平台。平台面向普通消费者、入驻商家、配送骑手以及平台管理员四类角色，聚焦外卖点餐核心业务，简化冗余功能，满足社区范围内外卖业务使用需求。

## 2 总体描述

### 2.1 产品定位

“吃了么”是一个**面向社区中小型餐饮场景的轻量化外卖平台**。与美团、饿了么等头部平台相比，本平台不做全品类覆盖与大规模运力调度，而是聚焦“一家社区小店如何把一份餐送到楼下”的最小完整闭环：

- **轻**：单个部署实例即可支撑一个社区范围内的多商户运营；
- **全**：覆盖“浏览 → 下单 → 支付 → 接单 → 配送 → 完成 → 评价”的完整业务链路；
- **稳**：以订单状态机与多角色权限隔离作为系统稳定性的两条主线。

### 2.2 用户角色

系统划分四个角色，各角色职责与核心诉求如下：

| 角色 | 标识 | 核心诉求 | 使用频率 |
| --- | --- | --- | --- |
| 普通用户 | `CONSUMER` | 快速找到想吃的、下单顺畅、能看到餐到哪了 | 高频，移动端为主 |
| 入驻商家 | `MERCHANT` | 菜品好上架、来单有提醒、出餐不出错 | 高频，桌面端为主 |
| 骑手 | `RIDER` | 有单可接、路线清楚、状态更新快 | 高频，移动端为主 |
| 平台管理员 | `ADMIN` | 审核有据、数据可查、异常可干预 | 低频，桌面端为主 |

## 3 业务流程分析

### 3.1 主业务流程

平台的核心业务是一条跨四个角色的长链路，任一环节的状态变更都必须被记录且可追溯。

```
普通用户                商家                    骑手                 管理员
   │                     │                       │                     │
   ├─ 浏览店铺/菜品 ────> │                       │                     │
   ├─ 加入购物车         │                       │                     │
   ├─ 提交订单 ────────> ├─ 接收新订单          │                     │
   ├─ 支付订单           ├─ 确认接单 ──────────> ├─ 查看待配送订单     │
   │                     ├─ 备餐/出餐           ├─ 抢单/接单          │
   │                     │                       ├─ 取餐                │
   │  <──── 查看配送进度 ─┼───────────────────────┤ 配送中              │
   │                     │                       ├─ 确认送达           │
   ├─ 确认收货            │                       │                     │
   ├─ 评价订单 ────────> ├─ 查看评价             │                     │
   │                     │                       │                     ├─ 审核商家/骑手
   │                     │                       │                     ├─ 数据统计
   │                     │                       │                     ├─ 订单干预
```

### 3.2 订单状态流转

订单状态机是本系统最核心的领域模型，共定义 8 个状态，状态之间只允许以下合法迁移。

| 状态码 | 状态名 | 触发方 | 说明 |
| --- | --- | --- | --- |
| `PENDING_PAYMENT` | 待支付 | 用户下单 | 订单已创建，等待用户完成支付 |
| `PENDING_ACCEPT` | 待接单 | 用户支付成功 | 已支付，等待商家确认接单 |
| `PREPARING` | 备餐中 | 商家接单 | 商家已接单，正在制作 |
| `PENDING_DELIVERY` | 待配送 | 商家出餐 | 餐品已做好，等待骑手取餐 |
| `DELIVERING` | 配送中 | 骑手取餐 | 骑手已取餐，正在配送 |
| `COMPLETED` | 已完成 | 用户确认收货 / 骑手送达 | 交易成功结束 |
| `CANCELLED` | 已取消 | 用户 / 商家 / 系统超时 | 交易取消，需按规则退款 |
| `REFUNDING` | 退款中 | 用户申请 / 系统 | 退款流程进行中 |

状态迁移规则：

| 当前状态 | 可迁移至 | 触发条件 | 操作者 |
| --- | --- | --- | --- |
| `PENDING_PAYMENT` | `PENDING_ACCEPT` | 支付成功回调 | 系统 |
| `PENDING_PAYMENT` | `CANCELLED` | 用户主动取消 / 超时 15 分钟未支付 | 用户 / 系统 |
| `PENDING_ACCEPT` | `PREPARING` | 商家确认接单 | 商家 |
| `PENDING_ACCEPT` | `REFUNDING` | 商家拒单或超时 10 分钟未接单 | 商家 / 系统 |
| `PREPARING` | `PENDING_DELIVERY` | 商家标记出餐 | 商家 |
| `PENDING_DELIVERY` | `DELIVERING` | 骑手确认取餐 | 骑手 |
| `DELIVERING` | `COMPLETED` | 骑手确认送达 | 骑手 |
| `DELIVERING` | `REFUNDING` | 用户申诉配送异常 | 用户（需管理员介入） |
| `COMPLETED` | — | 终态，不可再迁移 | — |
| `CANCELLED` | — | 终态，不可再迁移 | — |
| `REFUNDING` | `CANCELLED` | 退款完成 | 系统 |

> **设计要点**：所有状态迁移必须在服务端校验，前端按钮的显隐只是体验优化，不构成权限边界。状态变更需同时写入 `order_status_log` 表，记录操作者、原状态、新状态与时间，用于纠纷追溯。

### 3.3 关键子流程

**下单流程**：用户提交购物车 → 服务端校验菜品是否在售、库存是否充足、是否达到起送价 → 计算配送费与优惠 → 生成订单（含订单号、明细快照）→ 扣减库存 → 返回支付参数。

**配送流程**：商家出餐后订单进入“待配送”池 → 骑手端轮询/推送获取可抢订单 → 骑手抢单（乐观锁防并发）→ 取餐 → 送达 → 订单完成。

**评价流程**：订单完成后 7 天内，用户可对店铺与配送各提交一次评价；评价内容需经敏感词过滤；商家可回复一次评价。

### 4.6 需求优先级说明

- **P0（必须实现）**：构成业务闭环的最小集合，缺失则系统无法演示完整流程；
- **P1（应该实现）**：显著影响使用体验，是答辩加分项；
- **P2（可以实现）**：增强型功能，在时间允许时实现。

## 6 可行性分析

### 6.1 技术可行性

本系统所采用的技术栈均为业界成熟方案：

- **SpringBoot**：简化 Spring 配置，内置 Tomcat，生态完善，是当前 Java Web 开发的主流选择；
- **Spring Security**：提供认证、授权、CSRF 防护等完整安全能力，与 SpringBoot 无缝集成；
- **Vue 3 + Element Plus**：组合式 API 提升代码组织能力，Element Plus 提供完整的中后台组件；
- **MySQL**：成熟的关系型数据库，事务与索引能力满足订单系统的数据一致性要求。

上述技术本人已在课程学习中掌握，具备实现能力。技术方案不存在原理性障碍。

### 6.2 经济可行性

- 开发工具全部使用开源或社区版，无授权费用；
- 部署可采用本地环境或低成本云服务器（学生机约 10 元/月）；
- 无第三方商业服务依赖（支付采用模拟网关）；
- 总投入成本极低，经济上完全可行。

### 6.3 操作可行性

- 四类角色的操作流程均参照主流外卖平台设计，用户无需额外学习成本；
- 界面采用 Element Plus 标准交互范式，符合用户习惯；
- 系统部署为单体应用，运维复杂度低。

### 6.4 法律与合规可行性

- 系统为教学研究用途，不涉及真实交易与资金流转；
- 用户数据仅用于功能演示，不涉及真实个人信息的大规模采集；
- 采用的开源组件均遵循 MIT / Apache 2.0 等宽松许可证。

### 6.5 进度可行性

依据任务书安排的六个阶段，各阶段任务量与时间匹配，详见 [07-项目计划与进度管理](07-项目计划与进度管理.md)。关键风险已识别并制定应对措施，进度可控。
