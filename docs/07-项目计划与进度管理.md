## 5 风险管理

### 5.1 风险登记表

| 编号 | 风险描述 | 概率 | 影响 | 等级 | 应对措施 |
| --- | --- | --- | --- | --- | --- |
| R-01 | 订单状态机设计缺陷导致状态错乱 | 中 | 高 | 高 | 先画状态图再编码；用枚举约束迁移；写状态日志；补并发测试 |
| R-02 | 并发下单出现超卖 | 中 | 高 | 高 | 采用 `UPDATE ... WHERE stock >= ?` 原子扣减；JMeter 压测验证 |
| R-03 | 权限设计遗漏导致越权 | 中 | 高 | 高 | 接口级 + 数据级双层校验；编写 14 条越权用例专项测试 |
| R-04 | 前后端接口不一致导致联调返工 | 高 | 中 | 高 | 先定接口规范再并行开发；使用 Knife4j 生成在线文档 |
| R-05 | 论文与系统实现脱节 | 中 | 中 | 中 | 每完成一个模块立即截图存档，论文素材同步积累 |
| R-06 | 时间估算偏差导致延期 | 高 | 中 | 高 | 每周复盘进度；预留 2 周缓冲；关键路径任务优先 |
| R-07 | 环境差异导致部署失败 | 中 | 低 | 中 | 固定 JDK17、MySQL8 版本；配置项全部外置为环境变量 |
| R-08 | 电脑故障导致代码丢失 | 低 | 高 | 中 | 每日提交并推送远端；重要节点打 tag |

### 5.2 风险应对策略说明

**R-01 状态机风险**：这是本项目最核心的技术点，也是开题报告明确要解决的问题之一。应对的核心是"先设计后编码"——在 `02-概要设计说明书.md` 中用表格穷举了 8 种状态之间的合法迁移，在代码中用 `OrderStatusEnum.canTransitionTo()` 强制约束，在数据库中用 `order_status_log` 记录每一次变更，形成三重保障。

**R-02 超卖风险**：初版实现最容易犯的错误是"先 `SELECT` 查库存，再 `UPDATE` 减库存"，两步之间存在竞态窗口。正确做法是把判断与更新合并为一条 SQL，由数据库的行锁保证原子性。这一点已在详细设计中明确，并安排了专项压测。

**R-04 接口不一致风险**：前后端分离项目最常见的返工来源。应对方式是在编码前先把 74 个接口的路径、参数、响应结构全部固化到接口规范文档，前后端各自按文档开发，联调时只对差异部分。

## 6 质量保证

### 6.1 代码规范

| 项 | 规范 |
| --- | --- |
| Java 命名 | 类名大驼峰，方法名小驼峰，常量全大写下划线 |
| 分层职责 | Controller 只做参数校验与响应封装，业务逻辑全部在 Service |
| 异常处理 | 业务失败抛 `BizException`，禁止吞异常、禁止 `e.printStackTrace()` |
| 日志 | 使用 SLF4J，禁止字符串拼接，敏感信息脱敏 |
| SQL | 禁止 `SELECT *`，禁止字符串拼接 SQL，必须参数化 |
| 前端 | 遵循 ESLint + Prettier 配置，组件名大驼峰 |

### 6.2 代码评审要点

由于是单人项目，采用"自审清单"替代同行评审：

| 检查项 | 说明 |
| --- | --- |
| 权限校验 | 每个写接口是否校验了数据归属 |
| 事务边界 | `@Transactional` 是否覆盖了全部写操作 |
| 参数校验 | 是否使用 `@Valid` + 注解校验 |
| 空指针 | 是否处理了查询结果为 null 的情况 |
| 分页 | 列表接口是否强制分页，是否限制了最大 size |
| 敏感信息 | 日志与响应中是否泄露了手机号、身份证号 |

### 6.3 提交规范

遵循 Conventional Commits，详见 [08-Git协作规范](08-Git协作规范.md)。
