## 1 引言

### 1.1 编写目的

本文档定义“吃了么”外卖平台的数据库概念模型、逻辑结构与物理表结构，明确每张表的字段、类型、约束与索引设计，作为建库脚本编写与后端持久层实现的依据。

### 1.2 设计原则

| 原则 | 说明 |
| --- | --- |
| 第三范式为主 | 消除传递依赖，避免数据冗余；订单明细保存必要快照，属有意反范式 |
| 主键统一 | 所有表使用 `BIGINT UNSIGNED AUTO_INCREMENT` 主键 `id` |
| 逻辑删除 | 业务表统一使用 `deleted` 字段，不执行物理删除 |
| 时间可追溯 | 每表必备 `created_at`、`updated_at` |
| 金额精度 | 所有金额字段使用 `DECIMAL(10,2)`，禁止使用 `FLOAT` / `DOUBLE` |
| 状态枚举 | 状态字段使用 `TINYINT`，含义在注释中写明 |
| 索引适度 | 为高频查询字段建索引，避免过度索引影响写入 |

### 1.3 命名规范

| 对象 | 规范 | 示例 |
| --- | --- | --- |
| 表名 | 小写下划线，单数名词 | `orders`、`dish` |
| 字段名 | 小写下划线 | `created_at` |
| 主键 | `id` | `id` |
| 外键 | `<实体>_id` | `shop_id` |
| 普通索引 | `idx_<表>_<字段>` | `idx_orders_user_id` |
| 唯一索引 | `uk_<表>_<字段>` | `uk_sys_user_phone` |
| 布尔字段 | `is_` 前缀 | `is_open` |

## 2 E-R 模型设计

### 2.1 实体识别

| 实体 | 说明 | 对应表 |
| --- | --- | --- |
| 用户 | 平台所有账号，含消费者、商家、骑手、管理员 | `sys_user` |
| 收货地址 | 用户的配送地址 | `user_address` |
| 商家 | 商家资质信息 | `merchant` |
| 店铺 | 商家经营的线上店铺 | `shop` |
| 菜品分类 | 店铺内菜品分组 | `dish_category` |
| 菜品 | 可售商品 | `dish` |
| 购物车项 | 用户的待结算商品 | `cart_item` |
| 订单 | 一次交易记录 | `orders` |
| 订单明细 | 订单中的单项菜品 | `order_item` |
| 订单状态日志 | 订单状态变更历史 | `order_status_log` |

### 2.3 主要关系说明

| 关系 | 基数 | 说明 |
| --- | --- | --- |
| 用户–地址 | 1:N | 一个用户可有多个收货地址 |
| 用户–商家 | 1:1 | 一个用户最多申请一个商家身份 |
| 用户–骑手 | 1:1 | 一个用户最多申请一个骑手身份 |
| 商家–店铺 | 1:1 | 一个商家经营一家店铺（社区场景简化） |
| 店铺–分类 | 1:N | 一个店铺有多个菜品分类 |
| 分类–菜品 | 1:N | 一个分类下有多个菜品 |
| 用户–购物车项 | 1:N | 一个用户的购物车有多个待结算项 |
| 用户–订单 | 1:N | 一个用户有多笔订单 |
| 店铺–订单 | 1:N | 一个店铺有多笔订单 |
| 订单–明细 | 1:N | 一个订单含多个菜品明细 |
| 订单–状态日志 | 1:N | 一次订单有多次状态变更 |
| 订单–配送任务 | 1:1 | 一个订单对应一个配送任务 |
| 骑手–配送任务 | 1:N | 一个骑手可承接多个配送任务 |
| 订单–评价 | 1:1 | 一个订单最多一条评价 |

## 3 数据表设计

### 3.1 用户表 `sys_user`

存储平台全部账号，通过 `role` 字段区分四类角色。

| 字段 | 类型 | 允许空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT UNSIGNED | 否 | AUTO_INCREMENT | 主键 |
| `phone` | VARCHAR(20) | 否 | — | 手机号，登录账号 |
| `password` | VARCHAR(100) | 否 | — | BCrypt 哈希 |
| `nickname` | VARCHAR(50) | 是 | NULL | 昵称 |
| `avatar` | VARCHAR(255) | 是 | NULL | 头像 URL |
| `role` | VARCHAR(20) | 否 | 'CONSUMER' | 角色：CONSUMER/MERCHANT/RIDER/ADMIN |
| `status` | TINYINT | 否 | 1 | 1 正常，0 禁用 |
| `last_login_at` | DATETIME | 是 | NULL | 最后登录时间 |
| `created_at` | DATETIME | 否 | CURRENT_TIMESTAMP | 创建时间 |
| `updated_at` | DATETIME | 否 | CURRENT_TIMESTAMP ON UPDATE | 更新时间 |
| `deleted` | TINYINT | 否 | 0 | 逻辑删除 |

**索引**：

| 名称 | 类型 | 字段 | 说明 |
| --- | --- | --- | --- |
| `PRIMARY` | 主键 | `id` | — |
| `uk_sys_user_phone` | 唯一 | `phone` | 手机号唯一 |
| `idx_sys_user_role` | 普通 | `role`, `deleted` | 按角色筛选 |

```sql
CREATE TABLE `sys_user` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  `phone`         VARCHAR(20)     NOT NULL                COMMENT '手机号',
  `password`      VARCHAR(100)    NOT NULL                COMMENT 'BCrypt密码哈希',
  `nickname`      VARCHAR(50)     DEFAULT NULL            COMMENT '昵称',
  `avatar`        VARCHAR(255)    DEFAULT NULL            COMMENT '头像URL',
  `role`          VARCHAR(20)     NOT NULL DEFAULT 'CONSUMER' COMMENT 'CONSUMER/MERCHANT/RIDER/ADMIN',
  `status`        TINYINT         NOT NULL DEFAULT 1      COMMENT '1正常 0禁用',
  `last_login_at` DATETIME        DEFAULT NULL            COMMENT '最后登录时间',
  `created_at`    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `updated_at`    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  `deleted`       TINYINT         NOT NULL DEFAULT 0      COMMENT '逻辑删除 0正常 1删除',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_sys_user_phone` (`phone`),
  KEY `idx_sys_user_role` (`role`, `deleted`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='系统用户表';
```

**索引**：`idx_oplog_operator` (`operator_id`, `created_at`)；`idx_oplog_module` (`module`, `created_at`)

## 6 性能与优化设计

### 6.1 索引设计说明

| 表 | 索引 | 支撑的查询 |
| --- | --- | --- |
| `orders` | `idx_orders_user` | 用户端"我的订单"按状态筛选并按时间倒序 |
| `orders` | `idx_orders_shop` | 商家端订单列表 |
| `orders` | `idx_orders_status_created` | 定时任务扫描超时订单 |
| `dish` | `idx_dish_shop_status` | 店铺详情页菜品列表 |
| `delivery_task` | `idx_delivery_status` | 骑手端待抢单列表 |
| `review` | `idx_review_shop` | 店铺评价列表 |

### 6.2 索引注意事项

- **最左前缀**：`idx_orders_user (user_id, status, created_at)` 可支撑 `WHERE user_id=?`、`WHERE user_id=? AND status=?`、`WHERE user_id=? AND status=? ORDER BY created_at` 三类查询；
- **避免冗余索引**：已有 `uk_orders_order_no` 则无需再为 `order_no` 建普通索引；
- **区分度低的字段**：`status`、`deleted` 单独建索引区分度低，应与高区分度字段组合；
- **写入代价**：`dish` 表索引较多，库存扣减为高频写操作，需在压测中观察写入性能。

### 6.3 查询优化策略

| 场景 | 策略 |
| --- | --- |
| 订单列表 | 分页查询，避免深分页（推荐游标分页或限制最大页码） |
| 店铺详情 | 菜品与分类分两次查询后在内存组装，避免 JOIN 笛卡尔积 |
| 店铺评分 | 评价表实时 AVG 计算并缓存 5 分钟 |
| 月销量 | 定时任务每日凌晨汇总更新，避免实时 COUNT |
| 大字段 | `operation_log.request_params` 使用 TEXT，列表查询不 SELECT 该字段 |

### 6.4 容量估算

按社区场景 100 家商户、日订单 500 单估算：

| 表 | 日增 | 年增 | 备注 |
| --- | --- | --- | --- |
| `orders` | 500 | 18 万 | 主要增长表 |
| `order_item` | 1500 | 55 万 | 订单的 3 倍 |
| `order_status_log` | 2500 | 91 万 | 订单的 5 倍 |
| `operation_log` | 200 | 7 万 | — |
| 其他 | — | < 10 万 | 变化小 |

年数据量在百万级以内，单实例 MySQL 完全可承载，无需分库分表。
