### 2.2 建设目标

建设一套前后端分离的社区外卖平台，覆盖顾客、商家、骑手、系统管理员四类角色，支持从店铺浏览、下单支付、商家接单出餐、骑手抢单配送到评价售后的完整业务流转。

系统重点解决三个问题：一是四类角色之间的权限隔离与数据越权防护；二是订单在多方参与下的全流程状态流转与一致性保障；三是多表关联场景下的查询性能与并发下单时的库存正确性。

### 2.3 系统边界

平台自身承担用户与资质管理、店铺与菜品管理、购物车与订单处理、配送调度、评价与售后、内容与数据管理六类职责。

以下事项位于系统边界之外，由外部条件承担或不在本版实现：真实资金清算与银行通道、真实地图路径规划与实时定位、真实短信通道、真实支付机构的商户接入。上述事项在本版中采用模拟方式实现，具体见第 11 章。

## 3 使用角色

### 3.1 顾客端

顾客是平台的消费方，通过手机号注册并登录，浏览店铺与菜品、加入购物车、提交订单并完成支付，跟踪订单状态直至收货，收货后可对订单进行评价，遇到餐品质量或配送问题时提交售后申请。

顾客只能访问本人的地址、购物车、订单、评价与消息，不能访问他人数据，不能进入商家、骑手与管理端的任何界面。

### 3.2 商家端

商家是平台的供给方，提交入驻申请并上传营业执照与食品经营许可证，经平台审核通过后获得店铺管理权限。商家维护店铺信息、营业时间、配送范围与费用规则，管理菜品分类与菜品，处理顾客订单并完成接单、出餐，处理退款申请与评价回复，查看本店经营数据。

商家只能访问本店铺的数据，不能查看其他店铺的订单、菜品与经营数据，不能修改订单金额与配送信息。

### 3.3 骑手端

骑手是平台的配送方，提交入驻申请并上传身份证与健康证，经平台审核通过后获得接单权限。骑手设置接单范围与同时接单上限，从订单池抢单，到店取餐后送达顾客，确认送达完成订单，查看个人配送收入与单量统计。

骑手只能查看待配送订单与本人已接订单的配送所需信息，不能查看订单金额构成、不能修改订单状态以外的订单内容。

### 3.4 系统管理员端

系统管理员是平台的运营方，负责商家与骑手的资质审核、账号与权限管理、全平台订单监管与售后争议裁定、菜品与内容监管、平台参数与数据字典维护、数据看板查看。

系统管理员的核心职责包括三项：一是审核商家提交的营业执照与食品经营许可证、骑手提交的身份证与健康证，决定是否准予入驻；二是对顾客与商家之间的售后争议作出裁定，支持顾客则全额退款，支持商家则驳回申请；三是对违规商家、骑手、菜品与内容执行冻结、下架、删除等处置。

### 3.5 权限边界

| 角色 | 可访问范围 | 禁止访问范围 |
| --- | --- | --- |
| 顾客 | 本人资料、本人地址、本人购物车、本人订单、本人评价、本人消息、公开店铺与菜品 | 他人数据、商家端、骑手端、管理端 |
| 商家 | 本店铺信息、本店铺菜品与库存、本店铺订单、本店铺评价、本店经营数据 | 其他店铺数据、顾客个人资料、骑手端、管理端 |
| 骑手 | 待配送订单、本人已接订单、本人收入与单量 | 订单金额构成、顾客完整资料、商家端、管理端 |
| 系统管理员 | 全平台用户、商家、骑手、订单、菜品、评价、公告、参数与统计 | 用户密码明文、支付凭证原文 |

权限校验分两层执行：接口层按角色拦截，数据层按归属校验。任何跨角色或跨归属的访问请求均被拒绝并记录日志。

## 10 非功能要求

### 10.1 性能要求

| 项 | 要求 |
| --- | --- |
| 列表类接口 | 单表分页查询响应时间不超过 300 毫秒 |
| 详情类接口 | 多表关联查询响应时间不超过 500 毫秒 |
| 订单提交 | 含库存扣减与订单写入，响应时间不超过 800 毫秒 |
| 并发下单 | 100 并发下不出现库存超卖与订单重复 |
| 并发抢单 | 50 并发下同一订单仅一名骑手抢单成功 |
| 缓存 | 字典与平台参数查询走本地缓存，命中率不低于 90% |
| 前端首屏 | 首页首屏渲染时间不超过 2 秒 |

### 10.2 安全要求

| 项 | 要求 |
| --- | --- |
| 密码存储 | 采用 BCrypt 加盐哈希，禁止明文或可逆加密存储 |
| 令牌 | 采用 JWT，有效期 2 小时，令牌载荷不包含密码与身份证号 |
| 越权防护 | 接口层按角色拦截，数据层按归属校验，跨角色与跨归属访问一律拒绝 |
| 注入防护 | 全部数据库操作使用参数化查询，禁止拼接 SQL 字符串 |
| 上传防护 | 校验文件头魔数、扩展名与大小，重命名后存储，禁止覆盖已有文件 |
| 登录限制 | 同一账号连续登录失败 5 次锁定 15 分钟 |
| 敏感信息 | 手机号在列表中脱敏展示，身份证号加密存储 |
| 异常处理 | 对外统一返回错误码与提示文案，不返回堆栈信息与数据库错误原文 |

### 10.3 可靠性要求

| 项 | 要求 |
| --- | --- |
| 状态一致性 | 订单状态变更通过状态机校验，非法迁移一律拒绝 |
| 幂等性 | 支付回调、库存回滚、重复提交等场景保证幂等，重复请求不产生重复结果 |
| 定时任务 | 订单超时取消任务每分钟执行一次，单次执行时间不超过 30 秒 |
| 事务 | 订单创建、取消、退款等涉及多表的操作在同一事务内完成 |
| 数据恢复 | 数据库每日全量备份，保留最近 7 天 |

### 10.4 兼容性要求

| 项 | 要求 |
| --- | --- |
| 浏览器 | 支持 Chrome、Edge、Firefox 最近两个大版本 |
| 分辨率 | 适配 375 像素至 1440 像素宽度，移动端与桌面端均可正常操作 |
| 接口 | 统一采用 JSON 格式与 UTF-8 编码，时间统一使用 `yyyy-MM-dd HH:mm:ss` |

### 10.5 可维护性要求

| 项 | 要求 |
| --- | --- |
| 分层 | 按控制层、业务层、数据访问层分层，层间通过接口调用 |
| 命名 | 类名、方法名、变量名与数据库字段名统一采用英文，遵循各自语言的通行规范 |
| 注释 | 公共类与核心方法写明用途、入参、出参与异常 |
| 接口文档 | 接口变更同步更新 Knife4j 注解，保持文档与实现一致 |
| 日志 | 分级记录，业务异常记录警告级别，系统异常记录错误级别并保留调用链标识 |
| 版本管理 | 全过程使用 Git 管理，遵循分支模型与提交信息规范 |

## 13 验收标准

### 13.1 功能验收

1. 第 5 至第 9 章所列 P0 功能全部可用，主业务流程从注册、浏览、下单、支付、接单、出餐、抢单、取餐、送达到评价可完整走通；
2. P1 功能的实现比例不低于 90%，未实现的项在验收记录中逐条说明原因；
3. 四类角色的权限边界与第 3.5 节一致，跨角色与跨归属访问均被拒绝；
4. 订单状态流转符合状态机定义，非法迁移无法通过接口触发；
5. 并发下单不出现库存超卖，并发抢单不出现一单多骑手。

### 13.2 文档验收

1. 第 12 章所列文档齐备，章节结构与论文提纲对应；
2. 文档中的功能编号与本文档一致；
3. 接口文档与实际接口一致，可通过 Knife4j 在线查看；
4. 论文正文不少于 1 万字，格式符合学院要求。

### 13.3 代码验收

1. 代码按控制层、业务层、数据访问层分层，无跨层调用；
2. 密码采用哈希存储，数据库操作全部参数化；
3. 关键业务方法有注释，异常统一处理；
4. 提交历史遵循分支模型与提交信息规范，每个提交可独立编译。

### 13.4 答辩验收

1. 可现场演示完整下单流程与后台审核流程；
2. 可说明多角色权限隔离与订单状态流转的实现方式；
3. 可回答关于数据库设计、并发控制与安全措施的提问。
