## 1 引言

### 1.1 编写目的

本文档在需求规格说明书的基础上，确定“吃了么”外卖平台的总体技术架构、分层结构、功能模块划分、核心机制与关键设计决策，作为详细设计与编码实现的直接依据。

### 1.2 设计原则

| 原则 | 说明 | 在本项目中的体现 |
| --- | --- | --- |
| 单一职责 | 一个类/模块只承担一项职责 | Controller 只做参数校验与响应封装，业务逻辑全部下沉 Service |
| 分层解耦 | 层与层之间单向依赖 | Controller → Service → Mapper → DB，禁止反向依赖 |
| 契约优先 | 接口先行，前后端并行开发 | 先定义 RESTful 接口契约（见 05-接口设计规范），再分别实现 |
| 防御式编程 | 不信任任何外部输入 | 全链路参数校验 + 全局异常处理 |
| 状态受控 | 关键实体状态只能通过受控迁移改变 | 订单状态机 + 状态日志表 |
| 约定优于配置 | 减少样板代码 | MyBatis-Plus 自动 CRUD、Spring Boot 自动装配 |

## 2 系统总体架构

### 2.1 架构风格

系统采用**前后端分离的 B/S 架构**，前端为独立的 Vue 3 单页应用（SPA），后端为 SpringBoot 提供的 RESTful API 服务，二者通过 HTTP/JSON 通信，通过 JWT 令牌完成无状态认证。

选择前后端分离而非传统服务端渲染的理由：

1. 用户端与骑手端需要移动端适配，SPA 一次开发可同时服务 PC 与移动端；
2. 后端 API 可独立测试与扩容，符合当前主流工程实践；
3. 便于在毕业设计答辩中清晰展示分层与接口设计。

## 3 分层设计

### 3.1 后端分层

| 层次 | 职责 | 允许依赖 | 禁止事项 |
| --- | --- | --- | --- |
| `controller` | 接收 HTTP 请求、参数校验、调用 Service、封装响应 | `service`、`common` | 禁止写业务逻辑、禁止直接调用 Mapper |
| `service` | 业务编排、事务边界、领域规则校验、跨模块调用 | `mapper`、`common`、其他 `service` | 禁止出现 `HttpServletRequest` 等 Web 对象 |
| `mapper` | 数据库访问，仅做 CRUD 与查询 | `entity` | 禁止写业务判断 |
| `entity` | 数据库表映射对象 | 无 | 禁止承载业务方法 |
| `dto` | 数据传输对象（请求/响应） | 无 | 禁止直接暴露给前端以外的场景 |
| `vo` | 视图对象（响应展示） | 无 | 禁止包含敏感字段 |
| `common` | 通用工具、异常、常量、响应封装 | 无 | 禁止依赖业务模块 |

依赖方向严格单向：`controller → service → mapper → entity`。跨模块调用只允许 Service 之间通过接口调用，禁止 Controller 互相调用。

### 4.2 用户模块设计

**职责**：账号生命周期管理、资料维护、收货地址管理。

**核心用例**：

| 用例 | 前置条件 | 主流程 | 异常分支 |
| --- | --- | --- | --- |
| 注册 | 手机号未被占用 | 校验手机号 → 校验密码强度 → BCrypt 加密 → 落库 | 手机号已存在 → 返回 1001 |
| 登录 | 账号存在且状态正常 | 校验密码 → 签发 JWT → 返回令牌与角色 | 密码错误 → 1002；账号禁用 → 1003 |
| 修改资料 | 已登录 | 校验字段 → 更新 → 失效缓存 | 手机号重复 → 1001 |
| 地址管理 | 已登录 | 增删改查 → 设置默认地址时清除其他默认 | — |

**关键设计**：

- 密码使用 `BCryptPasswordEncoder`，盐值随机，同一密码两次加密结果不同；
- JWT 载荷包含 `userId`、`role`、`exp`，不包含手机号等敏感信息；
- 用户状态分为 `NORMAL(1)`、`DISABLED(0)`，禁用用户的令牌在过滤器中被拒绝。

### 4.3 商家与店铺模块设计

**职责**：商家入驻申请、资质管理、店铺信息与营业状态。

**关键设计**：

- 商家入驻需提交资料，状态为 `PENDING(0)`，管理员审核通过后变为 `APPROVED(1)`，驳回为 `REJECTED(2)` 并记录原因；
- 商家与店铺为 1:1 关系，一个商家账号经营一家店铺（社区场景简化设计）；
- 营业状态 `is_open` 直接影响用户端店铺列表与下单校验，打烊店铺不可下单；
- 起送价 `min_order_amount` 与配送费 `delivery_fee` 由商家自设，下单时校验。

### 4.4 菜品模块设计

**职责**：分类管理、菜品 CRUD、库存、上下架、图片。

**关键设计**：

- 菜品与分类为 N:1 关系，分类删除前须校验其下无菜品；
- 菜品状态：`ON_SALE(1)` 在售、`OFF_SALE(0)` 已下架、`SOLD_OUT(2)` 售罄（库存为 0 时自动）；
- 库存扣减使用 `UPDATE dish SET stock = stock - #{n} WHERE id = #{id} AND stock >= #{n}` 的原子语句，返回受影响行数为 0 说明库存不足，直接抛业务异常；
- 菜品图片上传后返回访问 URL，数据库仅存储相对路径。

### 4.5 订单模块设计（核心）

**职责**：订单创建、支付、状态机流转、取消与退款、查询。

**订单创建流程**：

```
1. 校验用户登录态与账号状态
2. 从购物车读取选中项（或直接传入菜品与数量）
3. 校验店铺营业状态、是否在配送范围
4. 校验菜品是否在售、库存是否充足（逐项）
5. 计算商品总额，校验是否达到起送价
6. 计算配送费、优惠（本期无优惠券，预留字段）
7. 组装订单主表与明细快照（快照保存下单时的菜名与单价，避免菜品改价影响历史订单）
8. 开启事务：
   a. 插入 orders
   b. 批量插入 order_item
   c. 逐项原子扣减库存（失败则整单回滚）
   d. 清空已结算的购物车项
   e. 写入 order_status_log（null → PENDING_PAYMENT）
9. 返回订单号与支付参数
```

**状态机实现**：

采用**枚举 + 迁移表**的方式实现，而非大量 `if-else`：

```java
public enum OrderStatusEnum {
    PENDING_PAYMENT(0, "待支付"),
    PENDING_ACCEPT(1, "待接单"),
    PREPARING(2, "备餐中"),
    PENDING_DELIVERY(3, "待配送"),
    DELIVERING(4, "配送中"),
    COMPLETED(5, "已完成"),
    CANCELLED(6, "已取消"),
    REFUNDING(7, "退款中");

    private static final Map<OrderStatusEnum, Set<OrderStatusEnum>> TRANSITIONS = Map.of(
        PENDING_PAYMENT, EnumSet.of(PENDING_ACCEPT, CANCELLED),
        PENDING_ACCEPT,  EnumSet.of(PREPARING, REFUNDING),
        PREPARING,       EnumSet.of(PENDING_DELIVERY),
        PENDING_DELIVERY,EnumSet.of(DELIVERING),
        DELIVERING,      EnumSet.of(COMPLETED, REFUNDING),
        REFUNDING,       EnumSet.of(CANCELLED),
        COMPLETED,       EnumSet.noneOf(OrderStatusEnum.class),
        CANCELLED,       EnumSet.noneOf(OrderStatusEnum.class)
    );

    public boolean canTransitionTo(OrderStatusEnum target) {
        return TRANSITIONS.getOrDefault(this, Set.of()).contains(target);
    }
}
```

统一的状态变更入口：

```java
@Transactional(rollbackFor = Exception.class)
public void changeStatus(Long orderId, OrderStatusEnum target, Long operatorId, String remark) {
    Order order = orderMapper.selectById(orderId);
    OrderStatusEnum current = order.getStatus();
    if (!current.canTransitionTo(target)) {
        throw new BizException(ErrorCode.ORDER_STATUS_ILLEGAL);
    }
    // 乐观锁更新，防止并发重复流转
    int rows = orderMapper.updateStatus(orderId, current.getCode(), target.getCode());
    if (rows == 0) {
        throw new BizException(ErrorCode.ORDER_STATUS_CONFLICT);
    }
    orderStatusLogMapper.insert(new OrderStatusLog(orderId, current, target, operatorId, remark));
}
```

**订单号生成**：采用 `yyyyMMddHHmmss` + 6 位随机数 + 2 位用户ID取模，共 22 位，保证可读且冲突概率低。生产环境可替换为雪花算法。

**超时取消**：使用 Spring 的 `@Scheduled` 定时任务，每分钟扫描 `PENDING_PAYMENT` 且 `created_at < now - 15min` 的订单，执行取消并回滚库存。

### 4.6 配送模块设计

**职责**：待配送订单池、骑手抢单、取餐与送达确认。

**关键设计**：

- 商家出餐后创建 `delivery_task` 记录，状态 `WAITING(0)`；
- 骑手抢单使用**乐观锁**：`UPDATE delivery_task SET rider_id = ?, status = 1, version = version + 1 WHERE id = ? AND status = 0 AND version = ?`，受影响行数为 0 表示已被抢走；
- 抢单成功后同步变更订单状态为 `DELIVERING`；
- 距离计算使用 Haversine 公式，本地计算避免依赖地图 SDK；
- 骑手需通过管理员认证（`audit_status = 1`）方可抢单。

### 4.7 评价模块设计

**职责**：订单完成后的评价发表、商家回复、评价列表。

**关键设计**：

- 评价与订单为 1:1（一个订单一次评价），通过 `order_id` 唯一索引保证；
- 评价包含店铺评分（1–5）、配送评分（1–5）、文字内容、图片（可选）；
- 订单完成后 7 天内可评价，超期不可评价；
- 商家可回复一次，回复内容存储于评价表 `reply` 字段；
- 店铺评分由所有评价的算术平均实时计算，并缓存 5 分钟。

### 4.8 管理后台模块设计

**职责**：审核、管控、统计、干预。

**关键设计**：

- 管理员账号独立于业务用户，存储于 `sys_user` 表但角色为 `ADMIN`，或独立 `admin_user` 表（本项目采用前者，通过角色区分）；
- 所有写操作通过 AOP 切面记录到 `operation_log` 表；
- 异常订单干预（强制退款/强制完成）需二次确认并填写原因，操作不可撤销；
- 数据看板使用聚合 SQL 直接查询，避免引入额外的统计表。

### 4.9 权限设计

系统采用 **RBAC（基于角色的访问控制）** 模型，简化为一层角色直连权限：

```
用户 (sys_user) ──N:1──> 角色 (role: CONSUMER/MERCHANT/RIDER/ADMIN)
                              │
                              └──> 接口权限（通过 @PreAuthorize 注解声明）
```

**实现方式**：

1. 登录时 JWT 载荷写入 `role`；
2. `JwtAuthenticationFilter` 解析令牌后构造 `Authentication`，权限为 `ROLE_<role>`；
3. Controller 方法上使用 `@PreAuthorize("hasRole('MERCHANT')")` 声明式控制；
4. 数据级权限（如商家只能操作自己的菜品）在 Service 层校验归属关系。

**越权防护要点**：

- 存在 `merchantId`/`shopId` 参数的接口，必须在 Service 层校验其归属当前登录用户；
- 订单查询必须附加 `userId = 当前用户` 或 `merchantId = 当前商家` 的过滤条件；
- 禁止仅依赖前端隐藏按钮。

## 5 数据库设计概要

详细的表结构见 [04-数据库设计说明书](04-数据库设计说明书.md)，本节仅说明数据架构的整体思路。

### 5.1 实体关系

核心实体共 12 张表，主要关系如下：

```
sys_user (1) ──── (1) merchant ──── (1) shop
    │                                    │
    │                                    ├── (N) dish_category ─── (N) dish
    │                                    │
    ├── (N) user_address                 ├── (N) orders
    │                                    │        │
    ├── (N) cart_item ─── (N) dish       │        ├── (N) order_item
    │                                    │        │
    └── (N) review <─────────────────────┘        ├── (N) order_status_log
                                                  │
                                          (1) delivery_task
                                                  │
                                              rider (sys_user)
```

### 5.2 命名规范

| 对象 | 规范 | 示例 |
| --- | --- | --- |
| 表名 | 小写下划线，业务表用单数 | `orders`、`dish`、`delivery_task` |
| 字段名 | 小写下划线 | `created_at`、`is_open` |
| 主键 | 统一命名 `id`，BIGINT 自增 | `id` |
| 外键 | `<实体>_id` | `shop_id`、`user_id` |
| 时间字段 | 每表必备 `created_at`、`updated_at` | — |
| 逻辑删除 | `deleted` TINYINT(1)，0 正常 1 删除 | — |
| 索引 | `idx_<表>_<字段>` | `idx_orders_user_id` |
| 唯一索引 | `uk_<表>_<字段>` | `uk_sys_user_phone` |

### 5.3 数据一致性策略

| 场景 | 策略 |
| --- | --- |
| 订单与库存 | 同一数据库事务，库存原子扣减，失败整单回滚 |
| 订单状态变更 | 乐观锁 + 状态日志，保证幂等与可追溯 |
| 抢单 | 乐观锁 `version` 字段 |
| 支付回调 | 幂等键（订单号）去重 |
| 评价唯一性 | `order_id` 唯一索引 |

### 6.3 错误码规范

| 区间 | 含义 | 示例 |
| --- | --- | --- |
| 0 | 成功 | — |
| 1000–1999 | 认证与账号 | 1001 手机号已注册、1002 密码错误 |
| 2000–2999 | 权限 | 2001 无访问权限、2002 令牌过期 |
| 3000–3999 | 参数校验 | 3001 参数缺失、3002 参数格式错误 |
| 4000–4999 | 业务规则 | 4001 库存不足、4002 未达起送价、4003 订单状态非法 |
| 5000–5999 | 系统与外部依赖 | 5001 系统内部错误、5002 文件上传失败 |

## 7 安全设计

### 7.1 认证流程

```
客户端                          服务端
   │                              │
   ├─ POST /api/v1/auth/login ───>│
   │                              ├─ 查询用户
   │                              ├─ BCrypt 校验密码
   │                              ├─ 生成 JWT (HS256, 2h)
   │  <──── { token, role, ... } ─┤
   │                              │
   ├─ GET /api/v1/orders          │
   │  Header: Authorization:Bearer <token>
   │                              ├─ JwtAuthenticationFilter 解析
   │                              ├─ 校验签名与过期
   │                              ├─ 构造 Authentication
   │                              ├─ @PreAuthorize 校验角色
   │  <──── 200 { data } ─────────┤
```

### 7.2 安全措施清单

| 威胁 | 防护措施 |
| --- | --- |
| 密码泄露 | BCrypt 加盐哈希，cost=10 |
| 令牌伪造 | HS256 签名，密钥 ≥ 256 位，存于环境变量 |
| 令牌重放 | 有效期 2 小时 + 刷新令牌机制 |
| 越权访问 | 接口级 `@PreAuthorize` + 数据级归属校验 |
| SQL 注入 | MyBatis-Plus 参数化，禁止 `${}` 拼接 |
| XSS | 富文本白名单过滤，前端 `v-html` 谨慎使用 |
| CSRF | 无状态 JWT + 不使用 Cookie 传递令牌，天然免疫 |
| 暴力破解 | 登录失败 5 次锁定 15 分钟（Caffeine 计数） |
| 文件上传攻击 | 白名单校验扩展名与 MIME，重命名存储，禁止执行权限 |
| 敏感信息泄露 | 手机号/身份证号脱敏，异常响应不返回堆栈 |
| 越权删除 | 删除操作校验资源归属 |

### 7.3 密码与令牌策略

| 项 | 策略 |
| --- | --- |
| 密码长度 | 8–20 位 |
| 密码复杂度 | 必须包含字母与数字 |
| 加密算法 | BCrypt，cost=10 |
| JWT 算法 | HS256 |
| 令牌有效期 | 2 小时 |
| 刷新令牌 | 有效期 7 天，一次性使用 |
| 令牌存储 | 前端 localStorage（毕业设计），生产建议 httpOnly Cookie |

## 8 关键设计决策

| 编号 | 决策 | 备选方案 | 选择理由 |
| --- | --- | --- | --- |
| D-01 | 前后端分离 SPA | 服务端渲染 Thymeleaf | 需同时服务 PC 与移动端，SPA 复用性更好 |
| D-02 | JWT 无状态认证 | Session + Redis | 一期不引入 Redis，无状态降低部署复杂度 |
| D-03 | MyBatis-Plus | JPA / 纯 MyBatis | 通用 CRUD 减少样板代码，同时保留手写 SQL 能力 |
| D-04 | 订单状态机用枚举迁移表 | if-else 链 | 迁移规则集中可读，新增状态只需改枚举 |
| D-05 | 抢单用乐观锁 | 悲观锁 / Redis 分布式锁 | 并发量小，乐观锁无额外依赖，冲突时可重试 |
| D-06 | 模拟支付网关 | 接入真实沙箱 | 毕业设计不涉及真实资金，模拟支付可完整演示流程 |
| D-07 | 距离用 Haversine 本地计算 | 高德/百度地图 API | 避免依赖第三方密钥与配额，演示环境足够 |
| D-08 | 图片存本地文件系统 | 对象存储 OSS | 降低部署复杂度，接口抽象后可随时替换 |
| D-09 | 本地 Caffeine 缓存 | Redis | 一期单实例部署，本地缓存足够且零运维 |
| D-10 | 单体应用 | 微服务 | 社区场景业务量小，单体部署简单，符合毕业设计规模 |
